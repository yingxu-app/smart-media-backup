# Yingxu native mobile backup foundation

## Implemented in this change

- Pocket's React Native screen now contains an offline-first local backup flow. It starts without the desktop app or network, chooses source and destination folders through the platform picker, scans supported photo/RAW/video extensions, groups output by date/event/media type, copies file-by-file, verifies SHA-256, and records copied/skipped/failed counts locally.
- iOS folder access uses document-picker security-scoped URLs/bookmarks. Android uses Storage Access Framework tree grants. A revoked or unavailable grant produces an error and requires the user to choose the folder again.
- Android copies run under a data-sync foreground service with an ongoing notification. On backgrounding the JS task pauses at the next file boundary and remains recoverable; iOS is best-effort and requires reopening the app to continue after suspension. Relaunch recovery retries the task from the beginning, relying on hash-based duplicate detection to skip already-copied files.
- The paired desktop bridge can start the configured desktop backup, pause/resume it, cancel it, read status/history, and read/write shooting notes. It remains opt-in, bound to the paired TCP socket, and exposes no general desktop management endpoint. Starting a desktop job uses the desktop's already-configured source/target and asks for confirmation in the phone app.
- Phone-to-desktop transfer sends bounded Base64 chunks over the paired LAN TCP socket. The desktop writes only under its configured backup root at `影序手机备份/`, verifies the complete file SHA-256, and atomically renames it into place. Conflicts with identical hashes are skipped; different contents get a numbered filename. If the desktop is unavailable, the phone stores a queued task and retries it after the user reconnects.
- Desktop-to-phone import is now available for the most recent media scan in the desktop app. The paired TCP bridge gives the phone only an opaque per-connection source ID, safe display metadata, file size, and 1 MiB chunks; it does not return absolute paths. The phone writes into the user-authorized iOS folder URL or Android SAF tree, stages to a temporary file, verifies SHA-256, and only then commits the final filename. Matching destination hashes are skipped and conflicts receive numbered names. When interrupted, the app re-lists the desktop scan and resumes matching files by display metadata; completed files are skipped by hash. The desktop Settings panel shows the paired phone's sanitized import progress.
- Mobile Firebase REST support includes email/password account creation/login, refresh-token storage in iOS Keychain/Android Keystore-backed storage, user-scoped Realtime Database paths, live progress, and metadata-only history. The security rules deny anonymous access and isolate `/users/{uid}`. No photo/video bytes, local URIs, absolute paths, or credentials are included in metadata.
- Mobile cloud writes now keep a sanitized local outbox when network requests fail and retry it after account restoration or app foregrounding. Live progress contains status/counts/current filename, while the full per-file manifest is sent once with terminal history rather than repeated on every progress update; this limits unnecessary Firebase Spark quota use. Firebase path segments reject traversal and invalid key characters before network access.
- Desktop Firebase sync now has email login/refresh support, stores refresh tokens through the OS credential vault, publishes throttled live progress, and syncs sanitized local history/file names to the same user-scoped paths. Failed metadata writes are atomically persisted to a mode-restricted local outbox and retried on subsequent progress/history sync or session restoration. Configuration stores only the public project API key/URL, account email, UID, and a local device ID; password and refresh token are not written to `config.json`.
- Desktop Firebase sync now also subscribes to the authenticated user's Realtime Database `live` path using Firebase's REST event stream. The Settings page displays active progress from signed-in devices and refreshes its local view while open; terminal history and per-file metadata can be expanded from cloud history. Sign-out and project-setting replacement stop the stream. Desktop Firebase settings/history/live endpoints accept only loopback requests so local cloud metadata is not exposed directly over the LAN. This code path has mock/unit coverage but still requires live-project verification.
- The desktop Settings page now offers both Firebase account registration and sign-in. Registration uses Firebase Authentication's email/password endpoint; the password is cleared from the form after the request and is not stored in local configuration. A real user still needs to enter their password locally before account creation.
- The Mini Program source remains in the repository for reference, but its source checks were removed from active CI. The native Pocket app and desktop bridge are the active phone product.
- Mobile scans now prefer EXIF capture time on iOS and Android, falling back to file modification time where metadata is absent. This path is covered by the JS ordering test; native platform compilation and device metadata behavior still require CI/device evidence.
- The phone now persists local preferences for capture-time ordering, date folders, video inclusion, and source-folder preservation, and offers a share-sheet text report from local history. The report contains summary counts and file names only; a separately generated downloadable report file and additional naming patterns remain follow-up work.
- Existing archives can be selected as a separate copy-only import mode. Users can retain original subfolders or organize by date/event/type; source files are never deleted. History reports export their text and file summary through the operating-system share sheet.
